# CI & e2e (automação)

- **Builds Vercel só sob pedido do Thiago** (quota free esgota). O deploy é gated por `[deploy]` na mensagem do commit — sem a tag o Ignored Build Step cancela. Dia a dia: push de branch roda só CI do GitHub (gates/repo-guard/schema-contract) + **e2e local** — `supabase db reset` → restart `rest`+`kong` → `pnpm seed:e2e` + `seed:demo` → `pnpm build`/`start` em `:3100` **com `NEXT_PUBLIC_*` locais exportadas ANTES do build** (são embutidas no bundle; setar só no start não vale) → `pnpm test:e2e` (375 testes em 79 arquivos, zero quota, mesma cobertura do preview). `[deploy]` e e2e-preview só quando o Thiago autorizar — inclusive no squash de `main` (mensagem sem a tag não deploya prod; deploy manual fica pro Thiago).
- **Gate do push é o `e2e-app / e2e` (todo PR, backend local no runner). O preview valida o artefato.** Desde nov/2026 (cota de CPU da Vercel no limite) o `e2e-preview` é **opt-in**: só roda com `[e2e-preview]` na mensagem do commit — usar no último push do staging antes de subir pra `main`, não em toda rodada. Antes de pushar/mergear `main`: check do preview verde (quando a tag foi usada) ou avaliação explícita do Thiago — o Ignored Build Step da Vercel já pulou preview no passado sem aviso; o gate que não pula é CI + e2e-app. `main` deploya produção imediatamente, não existe segundo gate depois.
- **Migration nova também obedece a ordem:** aplicar no staging (`supabase db push --db-url postgresql://postgres:<senha>@db.onkosatlcvircdrfgyzq.supabase.co:5432/postgres`) antes ou junto do push da branch — senão o e2e-preview do app real quebra. **Produção recebe as migrations na janela do release** (PR `staging → main`), não no meio do backlog: o `schema-contract` dos PRs de feature compara contra **staging**; o check contra **prod** roda no release (PR para `main` ou push em `main`). As 30 migrations de 0178–0209 são aditivas e compatíveis com o código que está em prod (assinaturas com default ou RPCs que o main não chama) — não há drift ao aplicá-las. Senha: dashboard → Database settings (nunca versionar).
- **Antes de escrever ou aplicar SQL contra o banco, conferir o schema real.** Nunca escrever DDL de memória: checar colunas (`information_schema.columns` ou MCP `list_tables`), policies (`pg_policies`), enums (`pg_enum`) e definições de função (`pg_get_functiondef`) no ambiente alvo. E nunca redigitar SQL no MCP `apply_migration` — passar o conteúdo **verbatim** do arquivo de migration (a versão que o staging já validou).
- `.github/workflows/ci.yml` — todo push/PR: `tsc --noEmit` + `eslint src/` + `vitest` + **schema-contract** (`scripts/check-schema-contract.mjs` compara `database.types.ts` com o OpenAPI do PostgREST remoto — falha se o código declara coluna que o remoto não tem; é o guard contra "migration não aplicada"). Secrets: `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` (produção).
- `e2e-app.yml` — **gate do dia a dia**: todo PR roda a suite inteira com **`supabase start` no runner** (migrations + seed + fixtures `seed:e2e`/`seed:demo` frescos, gate de freshness dos types) em **3 shards paralelos**, cada um com banco próprio — sem fila entre PRs, sem depender do staging; push novo no PR cancela o run anterior. O app do PR builda no runner (`pnpm build`+`start` em :3000). O job agregador `e2e` mantém o nome do **required check** `e2e-app / e2e` e falha se algum shard falhou/cancelou (skip contaria como verde). Nightly 10:00 BRT e `workflow_dispatch backend=staging` rodam serial contra o **Supabase de staging** (secrets `E2E_*`; guard falha se faltar secret ou a URL tiver o ref de prod) — canário do ambiente real. `maxFailures: 10` no CI corta run com backend quebrado em minutos (antes: staging lento → login 504 → run morria nos 70min).
- `e2e-preview.yml` — `deployment_status` do Vercel (state=success, env=Preview) + `[e2e-preview]` no commit → roda a suite inteira contra a `target_url`. Segue existindo como validação do artefato deployado (env/middleware da Vercel); o gate do push é o e2e-app. Secrets: `VERCEL_AUTOMATION_BYPASS` (mantido por segurança mesmo com SSO desligado) + `E2E_*` apontando pro staging.
- **Fila global `e2e-staging`** (só runs contra staging: nightly/dispatch do e2e-app e o e2e-preview): `concurrency.group` repo-wide compartilhado — as fixtures `e2e00000-*`/`de*` do staging são globais e dois runs simultâneos se apagam (flake). `cancel-in-progress:false` sempre: run cortado deixa fixture em estado parcial. Fixtures **não** são re-seedadas por run (pisos `convergirPiso` re-criam o volátil; re-seed por push derrubava o PostgREST free tier) — staging recriado → `pnpm seed:e2e` manual com `.env.staging`.
- `e2e-nightly.yml` — cron semanal (segunda 09:00 BRT; era diário até nov/2026, cota de CPU da Vercel): spec `demo` contra produção (público, sem secrets).
- `deploy.yml` — **legado**: pipeline self-hosted (imagem → GHCR → SSH). A Vercel serve staging e produção; o workflow só roda à mão (`workflow_dispatch`) e o job interno exige `[deploy]` na mensagem — travado por `tests/deploy-gates.test.ts`.
- `repo-guard` (job do `ci.yml`, script `scripts/repo-guard.mjs`) — guarda anti-regressão de agente, 10 regras baratas em Node puro: **R1/R9** migrations do base imutáveis e numeração crescente (o ledger não se edita — a `0178` reaplicada verbatim na `0205` é o precedente), **R2** objeto criado em migration presente em `database.types.ts`, **R3** nenhum `.env*`/segredo versionado, **R4** bloco `nextjs-agent-rules` do `AGENTS.md` intacto, **R5** links relativos de docs, **R6** actionlint (WARN se o binário não existir), **R7** node coerente com `engines`, **R8** `next-env.d.ts` no estado do `next dev`, **R10** JSON/scripts válidos. Base do PR via `BASE_REF` (default `origin/main`); roda local com `pnpm guard`.
- `eval-gate.yml` — evals da Liza em PRs que tocam a superfície de IA (`tests/evals/**`, `src/lib/ia/**`, `src/app/api/ia/**`, componentes do assistente, migrations, `scripts/eval-ia.mjs`); modelos free do catálogo do provider; sem `IA_API_*` fica informativo (job `segredos` avisa, eval pula).
- `tests/deploy-gates.test.ts` e `tests/jobs-registry.test.ts` — os contratos acima viraram teste: apagar um `if:`, soltar um cron novo sem bearer ou renomear chave do JOBS fica vermelho no `pnpm test`, sem esperar o runner.
- **Proteção de branch (hoje desligada — opt-in do Thiago)**: `main` e `staging` não têm proteção na API. Quando ligar, os required checks são `gates`, `repo-guard`, `schema-contract` e `e2e-app / e2e`:
  ```bash
  gh api -X PUT repos/leomedeirosrlz/mentoria-ong-talento/branches/main/protection \
    -f required_status_checks='{"strict":true,"contexts":["gates","repo-guard","schema-contract","e2e-app / e2e"]}' \
    -F required_pull_request_reviews=null -F restrictions=null -F enforce_admins=false
  ```
  `enforce_admins:false` mantém o fluxo `staging → main` com `[deploy]` funcionando; `CODEOWNERS` passa a ser exigido só quando reviews obrigatórias entrarem.
- Playwright: `pnpm test:e2e` / `:demo` / `:app`; `E2E_BASE_URL` aponta o alvo (default localhost). Specs `tests/e2e/demo` são seguras em qualquer ambiente (não escrevem); `tests/e2e/app` fazem login real por senha + writes — rodam no e2e-app (runner → staging), nos previews e no stack local do dispatch `backend=local`; hard-stop se `E2E_SUPABASE_URL` contiver o ref de prod.

- **Convenção de piso nos specs app**: quem depende de fixture compartilhada **re-cria** o que precisa no beforeEach (padrão `convergirPiso` — PATCH-only morre em retry depois que o afterAll de outro arquivo deleta a row). Asserts pós-write usam `{ timeout: 15_000 }` — o roundtrip server action + `router.refresh()` em preview frio passa dos 5s default.
- **Previews públicos**: `ssoProtection` do projeto = `null` — URLs `.vercel.app` abrem sem SSO da Vercel (a auth do app segue valendo; signup é allowlist; Vercel manda `x-robots-tag: noindex` em previews). Todo deploy tem alias de branch: `realizavc-git-<branch>-thisux1s-projects.vercel.app`.
